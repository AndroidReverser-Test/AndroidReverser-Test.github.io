同一段代码，为什么执行与读取可以看到不同内容？

从零理解 UROV 的内存读取覆盖原理

发表于 2026 年 11 月 14 日 · AI逆向

调用一个函数，是让处理器执行其中的指令；把函数地址传给一个读取函数，是把这些指令当作普通字节取出来。两种操作访问的地址可以相同，目的却不同。

urov-lab 中的 UROV-Z 利用了这一区别：让处理器继续执行真实代码页，同时为指定代码页的数据读取提供一份由调用者指定的内容。 本文把这种机制称为“读取覆盖”，把提供给读取者的替代内容称为“影像”。

这里的“读取返回值”，指内存读取指令得到的数据，或者内核代读交付的字节。例如 LDR X2, [X0] 的结果进入 X2；它不等于某个 C 函数的返回值，也不要求修改函数返回寄存器。

本文沿着“准备运行环境 → 注册代码页 → 处理读取 → 更新影像 → 跟踪映射 → 撤销覆盖”的顺序解释实际实现。代码片段均为帮助理解的简化示意。

图 1：真实代码页负责执行，内核影像负责受支持路径上的数据读取。两者之间的分流由页权限和异常处理共同完成。

一、先补上六个必要概念

理解这套框架不需要先学完整的操作系统课程，但需要知道下面几件事。

概念 通俗解释 在 UROV 中的作用
用户态与内核态 应用运行在受限制的环境中；内核负责管理内存、进程和硬件 应用发起读取，内核接住特定的访问异常
虚拟地址与物理页 应用使用的是虚拟地址，处理器通过映射找到实际存储字节的物理内存 同一虚拟地址的执行仍落到真实代码页
内存页 内存管理的固定大小单位，一段代码可能占用很多页 权限陷阱按整页设置，不能只拦页内几个字节
页表与 PTE 页表是地址转换目录；末级页表项 PTE 记录物理页及访问权限 框架修改其中的数据访问权限
异常 CPU 暂停当前指令，把处理权交给内核的一种机制 数据读取被权限挡住后，框架接手续做该指令
寄存器与 PC 寄存器是 CPU 的小型工作区；PC 记录执行位置 框架把读取结果填入寄存器，再让 PC 前进

还会遇到两个 Linux 名词：mm 代表一个进程的地址空间，VMA 表示其中一段具有相同映射属性的地址范围。例如，一段来自共享库文件、可读可执行的代码映射就是一个 VMA。线程通常共享同一个 mm；创建独立地址空间的子进程则拥有另一个 mm。

VMA 描述“这段地址应当怎样使用”，PTE 决定“这一页当前怎样被硬件访问”。 UROV 保留代码映射本来的读执行语义，暂时收紧硬件的数据访问权限，再负责完成因此产生的读取。

页大小也不是写死的常数。框架从运行环境取得页表配置，按实际页大小计算边界和分配影像；当前实现接受的基础页大小是 4 KiB 和 16 KiB。

二、先看整体：谁负责配置，谁负责交付字节

UROV 是由 KernelPatch 装载的 KPM 模块。KernelPatch 提供模块入口、内核符号查找和函数挂接设施；UROV 在这些设施之上实现页管理和读取覆盖。所谓挂接，也就是在某个内核函数运行前后插入自己的处理逻辑。

从职责上看，框架分成三个部分：

部分 处理的问题 主要源码
控制入口 注册哪些页、使用什么影像、何时更新和注销 api/src/urov.c、backend.c 的 dispatch
读取处理 一次 CPU 读取或内核代读应交付哪些字节 uz_abort_before、uz_emulate_load、各类读取回调
状态维护 页是否仍属于原映射、缓冲区能否回收、子进程如何继承 页表访问、读者计数、映射回调和子映射管理

控制请求有两个入口。管理员通过 KPM 控制接口管理模块配置；应用通过用户态 API，把注册、更新等请求封装成带认证信息的 prctl 调用。prctl 原本就是 Linux 的进程控制系统调用，模块在其中识别属于自己的请求，其余调用保持原来的处理方式。

应用请求由 uz_prctl_before 检查，再由 dispatch 分派。请求认证使用模块密钥及请求认证标签；涉及会话的操作还检查地址空间所有权。知道某个会话编号，并不等于可以修改其他进程的影像。

全局只有一个活动主会话 g_sess。它绑定 owner 的 mm，里面包含一组受管页。同一地址空间中的线程共享该会话；fork 子地址空间使用专门的独立影像槽。

模块显示的 callers=all，表示在受管映射及已支持的读取路径中，不按照读取指令的调用位置挑选读者。它的作用范围仍由地址空间、受管页和具体读取路径决定。

三、关键步骤一：模块加载时，先建立处理能力

模块被加载与某页开始覆盖，是两个独立动作。加载阶段由 module_init 调用 urov_z_backend_init，主要完成以下准备。

1. 读取配置，建立认证状态

后端解析模块密钥、页数和内存预算、子影像配额，以及可选功能的开关。密钥用于派生请求认证所需状态。此时还没有修改任何应用代码页。

2. 认识当前内核的数据结构

不同内核中，task_struct、mm_struct 等结构的字段位置，以及部分内核函数的参数形式，可能不同。模块不能假设“某字段永远位于固定偏移”。

为此，btf.h 和 compat.h 读取并验证 BTF 类型信息。可以把 BTF 理解为内核的“数据结构说明书”：它描述字段位置、类型大小和函数原型。BTF 可以来自运行内核，也可以来自与运行内核构建标识严格匹配的独立数据包。模块据此找到地址空间、VMA、寄存器状态等字段，并核对准备调用的函数接口。

后端还检查地址范围、页表层数、页大小和内核线性映射，选择符合条件的页表访问及页面引用辅助函数。关键条件无法确认时，初始化会拒绝继续；扩展能力则按实际具备的条件启用。

3. 安装控制、异常和映射回调

后端挂接 prctl 控制入口、数据异常入口 do_mem_abort，以及缺页处理入口 handle_mm_fault。后者很重要：Linux 可能重新建立某页的 PTE，框架需要在合适时机补回读取陷阱。

同时，它安装映射变更和进程复制相关回调，并在具备辅助函数时接入内核代读路径。向量寄存器处理、远程页引用等能力，需要相应接口和挂接都可用，不能仅凭找到一个函数名就宣称支持。

4. 发布就绪状态

基础设施准备完成后，后端发布 g_ready，允许控制请求进入。应用随后提交 REGISTER，才会真正建立受管页和权限陷阱。

源码还包含可选的 KCLF 共享库加载子系统。它与读取覆盖共享部分已核验的内核信息，但职责是处理用户态库加载。它读取真实内存时使用后端的内部访问入口，避免把影像误当作正在解析的 ELF 内容。理解读取覆盖的主链路，不需要先理解加载器的全部细节。

四、关键步骤二：注册一页，到底建立了什么

注册入口是 do_register。调用者提供目标页地址、替代字节的来源，以及替代内容在页内的位置和长度。后端把这些输入转成自己持有的完整页影像。

1. 固定输入和所属地址空间

后端先检查会话是否空闲、页数是否合理、请求字段是否有效，然后取得并持有当前 mm 的引用。引用的作用是保证后续仍然使用该地址空间时，它不会被提前释放。

多页描述符会被复制到内核中，按地址排序并拒绝重复页，同时保留调用者最初的描述符序号。这样，按地址查找可以高效完成，后续 SET_PAGE(index) 仍对应调用者原来指定的那一页。

2. 检查目标是否适合接管

validate_target_vma 要求整页位于有效文件映射中，具有读和执行权限，当前没有写权限。设备映射、巨大页等特殊形态不能直接套用这套普通页模型；共享文件映射还有额外限制。

页表检查是另一层约束：VMA 合格，不代表 PTE 就一定是可以安全修改的普通末级页表项。后端还要核对它的类型、权限及特殊标志。

模块记录文件对象和该页在文件中的位置，用于以后确认“这个地址是否仍然对应注册时的那一页”。匿名堆内存或任意 JIT 内存，不能仅因为里面有机器码就当作合格目标。

3. 建立三份页缓冲区

默认读执行模式为每个主会话页面建立三份页大小的缓冲区：

名称 可以怎样理解 用途
snapshot 真实字节的基准副本 提供原生指令内容及暂停期间的读取视图
image 目前对读者公开的完整页面 交付替代读取结果
spare 下一次更新的准备区 构造新影像，等待发布

page_build_image 先把真实代码页复制为 snapshot，再把它整体复制为 image，最后把调用者指定的窗口写入 image。

snapshot = 注册时读取到的真实代码页
image    = snapshot 的完整副本
image[覆盖窗口] = 调用者提供的字节

因此，窗口以外的读取也有明确答案：返回基准副本中相应位置的字节。调用者不需要为每个未修改的位置另外提供数据。

这里的“真实”指内存中实际存在的代码，不保证是磁盘最初的内容。如果注册之前已有其他机制修改代码，snapshot 捕获的就是修改后的内存。可选写入分支还会维护这个基准，所以它也不能被理解成永不改变的历史副本。

图 2：先准备完整可读的数据，再逐页安装陷阱，最后开放替代读取。

4. 先提供过渡视图，再修改页权限

注册不能先设置陷阱、再慢慢准备缓冲区。否则另一颗 CPU 可能已经被陷阱拦住，而内核还没有可以返回的内容。

实际顺序是：先发布活动会话、开放读者入口，但设置 g_suspend=1。这个标志表示暂不提供替代字节；已经进入框架的读取使用 snapshot。

之后，ap_arm_pages 逐页安装权限陷阱。所有页面成功后，才清除 g_suspend，让读取者开始使用 image。如果中途失败，就进入恢复流程，撤销已经安装的陷阱。

这一安排解决的是“异常到来时，处理状态必须已经可用”。它并不把任意多页、任意并发映射修改变成一个硬件原子操作。

五、关键步骤三：用页权限把读取引入内核

ARM64 的页表分别描述数据访问许可和执行许可。在本框架接受的页表配置下，普通用户态 RX 页允许读取和执行；UROV 清除其中的 PTE_USER，也就是这里的 AP[1] 位，同时保留物理页地址和用户执行权限。

属性 安装前 安装后
指向的物理页 真实代码页 同一真实代码页
用户态取指 允许 保持允许
用户态数据读取 硬件直接完成 触发权限异常
替代字节的存放位置 内核缓冲区 仍是内核缓冲区

因此，CPU 并没有自动把数据读取重定向到 image。它先发现权限不满足，进入内核，再由软件交付影像中的字节。数据访问和执行许可的区分，来自 Arm 的页表权限设计。Arm 内存属性与权限说明（PDF）

一个位的修改，为什么需要这么多保护

页表同时被多个 CPU、Linux 内存管理代码和硬件访问。正确修改权限，要解决三类问题。

第一，正在修改的映射和页表必须仍然存在。 pt_access.h 取得映射保护，沿有效的上级表定位目标，再通过内核原生辅助函数取得页表锁。PTE 指针只在受保护的范围内使用。Linux 的页表锁就是为串行化这些表项访问而设置的。Linux 页表锁说明

第二，不能覆盖别人刚写进去的其他位。 pt_leaf.h 根据刚读出的表项构造新值，再做比较交换：只有当前值仍与读取时一致，才写入。这样能够保留硬件可能并发更新的访问状态等信息。若页面属于连续 PTE 组，还需先由已核验的内核辅助函数拆分该组，不能只改其中一项就当作完成。没有可用的拆分辅助函数时，这类修改会被拒绝。

第三，处理器不能继续使用旧权限。 CPU 会把地址翻译和权限缓存在 TLB 中。修改 PTE 后，还必须使相关缓存失效，让后续访问重新取得权限。

还有一个细小但重要的顺序：代码先发布 armed=1，再让新 PTE 生效。armed 表示软件已准备处理这个陷阱。如此，另一颗 CPU 一旦看见新权限并进入异常，框架就能识别它。

六、关键步骤四：跟着一条 LDR 走完整个异常流程

假设应用执行下面这条 A64 指令：

LDR X2, [X0]

它的意思是：“从 X0 指向的地址读取 8 字节，放进 X2。”如果 X0 落在受管页内，硬件的数据权限检查会失败，接下来依次发生以下步骤。

图 3：每个步骤都为下一步提供依据。最后提交的是一条已完成读取指令应当产生的状态。

1. 接住异常，先判断是不是自己的

do_mem_abort 的前置回调 uz_abort_before 检查执行上下文和异常信息。这里需要认识两个名称：ESR 记录“为什么发生异常”，FAR 记录“出问题的访问地址”。

后端确认它来自 AArch64 用户态，是预期的末级数据权限错误，故障地址有效，并且对应受管地址空间和页面。随后还会复核当前 VMA 的身份及页面状态。

这一步保证普通空指针、真正没有读权限的页面，以及其他类型的异常不会被错误地转换成替代读取。

2. 取得 CPU 真正执行的那条机器码

光知道故障地址还不够。内核必须知道指令读取几个字节、写哪个寄存器、是否同时更新基址。

uz_fetch_insns 根据异常保存的 PC 取得操作码。若指令本身位于受管页，使用对应的原生 snapshot；若位于普通页，则尝试安全读取真实用户内存。

这一步不能使用 image。 影像是“读取代码时希望看到的字节”，可能与 CPU 正在执行的机器码完全不同。用影像解码，会得到错误的指令行为。

3. 解码：把机器码翻译成一次明确的读取任务

uz_emulate_load 调用 uro_decode，生成 uro_load 描述。描述包含有效地址、元素宽度、寄存器数量、总读取长度、目标寄存器、符号扩展和基址回写等信息。

以 LDR X2, [X0] 为例，可以得到：

起始地址 = X0 的当前值
读取长度 = 8 字节
目标寄存器 = X2
基址回写 = 无
完成后的 PC = 原 PC + 4

如果指令是 LDR X2, [X0], #8，还要在成功后把 X0 增加 8。读取 32 位寄存器、带符号扩展读取和一次读两个寄存器，也各有不同的结果规则。解码器的意义就在于把这些区别明确列出来。

后端接着检查完整访问范围，并确认 FAR 落在这次读取实际涉及的地址内。仅仅“机器码能解码”，还不足以批准访问。

4. 选出字节来源，先把数据读齐

单页普通读取可以直接从对应影像复制所需字节；跨页读取由 read_range 按页边界拆成几段。

例如，一次 16 字节读取跨过页边界，前 8 字节位于受管页，后 8 字节位于普通邻页：

受管页尾部 8 字节 ── 从该页 image 读取 ──┐
                                         ├─ 拼成 16 字节临时结果
普通页开头 8 字节 ── 安全读取真实内存 ──┘

受管段需要核对页状态和映射身份；普通段使用 nofault 读取辅助函数，即读取失败就返回错误，不让内部复制随意触发另一轮复杂缺页处理。

所有片段都准备成功后，才进入寄存器提交。这样，后半段失败时，不会留下“第一个目标寄存器已经变了，第二个还没变”的半成品状态。这个保证不等于一次跨多页读取一定来自同一个全局发布序号。

5. 把字节转换为寄存器结果

普通整数读取由 uz_commit 按小端规则组合数值，执行必要的符号扩展、32 位结果处理和基址回写，再把 PC 增加 4。A64 指令固定为 4 字节，所以这里的前进量不是读取数据的长度。

FP/SIMD 向量读取还需要处理向量寄存器。后端通过已核验的内核辅助函数保存和更新该线程的 FPSIMD 状态，并按指令语义排列元素。对这些路径，仅修改通用寄存器数组是不够的。

6. 返回用户态，从下一条指令继续

模拟成功后，回调设置 skip_origin=1，跳过 Linux 原来的异常处理函数。因为这次读取已经由框架完成，继续按普通权限错误处理会重复处置同一个异常。

异常返回时，应用看到的是已经填好读取结果的寄存器，以及指向下一条指令的 PC。从程序的执行顺序看，这条读取已经完成。

如果暂时无法取得映射保护，后端保留 PC 和寄存器，让原指令重试。若确认是自己的受管读取，却无法正确模拟，则进入失败处理并发送 SIGSEGV，不会随意制造一个结果。

解码器的能力为什么有边界

实现覆盖多种整数单读、成对读取、独占读取，以及部分 FP/SIMD 和 LD1～LD4 多结构读取。实际后端还处理若干需要转换的读取编码，但它并不是完整的 ARM64 指令集模拟器。

特殊向量上下文、未知编码和无法满足的地址条件，都可能被拒绝。module/emulate.c 是较小的基础模拟模型；真正运行中的读取链路应看 backend.c 的 uz_emulate_load，后者还负责跨页、FPSIMD 和并发状态。

七、关键步骤五：内核代读为什么需要另一套入口

应用自己执行 LDR 会经过用户态数据访问权限检查，但有些读取由内核完成。例如从 /proc/<pid>/mem 读取，或者调用 process_vm_readv。这些路径可能直接取得页面引用并复制字节，不一定产生相同的用户态异常。

因此，UROV 同时处理“已经复制好的结果缓冲区”和“即将交给调用者的页面引用”。

图 4：上路修改原生读取成功后的结果；下路准备独立影像页，供后续内核复制使用。

路径 A：原生函数先读取，再修正结果缓冲区

access_remote_vm 一类函数把目标进程内存读入内核缓冲区。uz_kread_after 在原生函数返回后工作：

  1. 检查操作是读取，并确认原生函数确实返回了有效字节。
  2. 只在实际成功返回的范围内，按页查找受管部分。
  3. 将其中应使用影像的片段替换成 image 中的对应字节。
  4. 保留非受管片段和原生调用本身的成功、失败及长度语义。

这一入口覆盖的是实际经过该内核函数的读取，包括相应的进程内存文件和 ptrace 读取通路。Linux 原来的访问权限检查仍然先发生。

路径 B：原生函数返回页面，框架替换页面引用

GUP 是“取得用户内存页面”的一组内核接口。可以把页面引用理解成“拿到这页内存的一张使用凭证”，后续调用者凭它复制数据，并在使用结束后归还。

process_vm_readv 的相关流程中，uz_vm_readv_before 建立本次调用的读者记录，并持有会话引用。原生 remote GUP 完成后，uz_pin_after 对命中的受管页执行：

  1. 分配一张独立物理页。
  2. 在页影像锁保护下，把选中的完整读取视图复制进去。
  3. 按原接口使用的 GET 或 PIN 规则，处理新旧页面引用。
  4. 把返回数组中的对应元素换成这张独立页。
  5. 让原生 process_vm_readv 从这些页面继续复制；调用结束后释放读者记录。

为什么不直接把模块的 image 内存交出去？因为后续调用者可能在影像更新、甚至会话撤销之后才释放页面。独立副本把两种寿命分开：模块管理自己的影像，调用者管理拿到的读取副本。

GET 和 PIN 也不能混用。它们具有不同的页面引用约定，必须用与取得方式匹配的释放操作；否则内容即使正确，页面寿命仍然会出错。Linux 页面固定与引用说明

fast GUP 还有单独的 uz_gup_after。它对符合条件的普通 GET 读取使用类似的独立页替换；写入、PIN、长期固定以及仅允许快速取页的请求，不属于这条读取替换分支。不能把“接入 GUP”理解成所有页面使用方式都已覆盖。

框架自己读取时，如何避免读到自己的影像

注册时复制真实页面、加载器解析内存，都需要看到真实字节。后端调用内核代读辅助函数时，会临时标记当前任务，让代读回调跳过这些内部操作；调用返回后即撤销标记。异常路径取得操作码时，则直接选择原生 snapshot，或通过 nofault 辅助函数读取真实用户内存。

否则可能形成循环：为了建立真实快照而读取代码，却再次被框架改成影像，最终丢失真实视图。

八、关键步骤六：影像如何在多线程读取时更新

SET_PAGE 不能直接往正在被读的 image 中逐字节写入。那样一个读取者可能先看到旧内容的前半段，再看到新内容的后半段。

当前实现把“准备新内容”“发布指针”“允许复用旧存储”分开处理。

图 5：发布新内容与回收旧存储不是同一个动作。必须先让旧读者退出，旧影像才能成为下一次更新的准备区。

1. 检查更新是否仍基于最新状态

do_set_page 检查会话 owner、页面是否仍有效，以及请求里的 expected_generation 是否与当前发布序号一致。不一致就返回重试错误，避免较旧的控制请求覆盖更新后的内容。

这里的 generation 是会话的并发更新序号，用来协调请求先后。

2. 在 spare 中准备替代窗口

新的窗口字节先复制到 spare。用户内存访问发生在页短锁以外，避免把可能耗时或需要其他内核操作的工作放进临界区。

3. 在短锁内构造完整页并发布指针

page_swap_image 取得该页短锁，用最新 snapshot 填充新窗口之外的区域，再把 image 指针原子切换到准备好的 spare，暂存旧 image，并更新窗口位置及长度。

这意味着 SET_PAGE 定义的是新的覆盖窗口。新窗口之外恢复为基准视图，不是把历次窗口永久叠加起来。

读取者复制影像时也取得同一把短锁。因此，一次受保护的拷贝不会与指针交换或对应的字节维护交叉进行。锁内只做内核缓冲区操作，不做内存分配、用户内存访问或会睡眠的工作。

4. 等旧读者结束，再复用旧 image

只有短锁还不够：会话、地址索引和缓冲区可能被更长的读取流程持有。因此框架还有 readers.h 中的两组读者计数，可以把它理解为两批“正在通行的人”。

读者进入时，在一个原子操作中选择当前批次并增加计数；退出时减去计数。写者发布新状态后切换批次，随后进入的读者计入新批次。旧批次归零后，才把暂存的旧 image 设为下一次 spare。

“入口是否关闭”“当前批次”“两批读者数量”放在同一个原子状态字中，避免出现读者在切换之后又误入旧批次的空隙。

整套并发保护可以分成三层：控制锁排列注册、更新和撤销的顺序；页短锁保护具体影像拷贝与发布；读者计数保护对象的存活时间。它们解决不同的问题，不能相互替代。

九、关键步骤七：页面搬家、重新缺页和 fork 时怎么办

注册成功并不意味着地址以后永远不变。应用可能解除映射、调整权限、移动映射，或者创建子进程。框架需要把这些动作纳入自己的状态管理。

1. 先区分“地址相同”与“仍是原来的页面”

假设某个地址先映射文件 A，随后解除映射，又在原地址映射文件 B。仅按虚拟地址查表，就会把 A 的影像错误交给 B。

mapping_identity.h 因而核对文件对象，以及当前地址对应的文件页号：

当前文件页号 = VMA 的起始文件页号 + 目标页在 VMA 内的相对页号

它必须与注册时记录的身份一致。身份检查使用受保护期间取得的字段信息，不把一个旧 VMA 指针长期留着继续解引用。

2. 移动映射时，更新目录而不搬动描述符

框架把页描述符放在稳定槽中，再用一个按虚拟地址排序的索引指向这些槽。可以把它看作“书放在固定书架上，查找目录另外维护”。

mremap 成功后，后端更新相关槽的地址，在备用索引中生成新目录并发布；旧索引等旧读者退出后才复用。这样，已有读者持有的描述符不会因为一次排序而换成另一页。

munmap 或覆盖原地址的映射成功后，对应页面会标为失去原映射；失败的系统调用不会被当作已经完成。权限变化则由专门回调同步处理。会产生未跟踪别名的部分复制映射形式会被拒绝。

3. 原生缺页完成后，重新核对并安装陷阱

某页的 PTE 可能被回收，然后由 Linux 的缺页处理重新建立。handle_mm_fault 相关回调在原生处理之后，通过 uz_rearm_checked 重新取得映射保护，核对 VMA、文件身份、页面状态和 PTE，再决定是否补回 AP 陷阱。

因此，want 与 armed 是两个字段：want 表示当前逻辑上需要陷阱，armed 表示实际安装状态。页面可以仍然需要覆盖，却暂时没有可供修改的驻留 PTE。

原生缺页完成与陷阱重装之间，也不能被当作对所有并发读者完全原子的过程。

4. fork 为子地址空间建立独立视图

共享 mm 的线程不需要新影像。创建独立地址空间的 fork 则先检查挂接能力和预留槽位；容量不足时拒绝，避免创建出没有完整跟踪状态的继承者。

在新任务开始运行前，uz_copy_mm_after 为子地址空间建立各页的 image 和 snapshot，复制相应映射身份和状态，并建立子页陷阱。

父进程之后执行 SET_PAGE，不会改变已经复制给子进程的影像；父进程移动或解除映射，也不会直接改写子进程的地址槽。子影像槽在会话范围内保留，因此配额不能简单理解成“此刻存活的子进程个数”。

这一继承机制面向 owner 创建的直接子地址空间。受管子进程再创建独立地址空间的请求会被拒绝；共享原地址空间的线程创建则另行处理。

十、读路径为什么还要考虑写入和原子指令

默认规则：真实写入会使页面退出覆盖

默认 writes=rx 的目标是稳定的读执行代码页。如果映射获得写权限，或者框架识别到真实写者到达，uz_retire_written_page 等路径会把页面标为失效、取消覆盖意图，并恢复相应数据访问权限。

这样做的原因是：真实代码一旦改变，已有 snapshot 和 image 可能不再表达预期关系。退出覆盖能够把控制交还原生内存语义。模块不会因此给原本不可写的 VMA 额外授予写权限。

可选写入分支：维护真实页与读取视图的关系

源码还保留可选写入支持。可识别的写入先检查地址和权限，再通过原生内存访问路径处理写时复制，即 COW：共享页需要修改时，由内核为写者建立私有副本。

写入真实页后，后端同步维护影像与基准视图；部分外部写入通路则记录前像，之后读取真实页并合并变化。这些分支需要额外的前后像缓冲区。

源码中的原生单步重放还依赖专门编译开关和调试回调，默认不开启。它的思路是临时恢复访问，让硬件执行一条指令，再取得后像、合并变化并重装陷阱。它不属于普通读取每次都要经过的流程，也不能代表任意外部写者都能被完整跟踪。

LL/SC：异常可能打断“先读后条件写”

ARM64 的一些原子操作使用独占读取与条件写入，例如 LDXR / STXR。可以把它想成：先登记某个位置，再尝试修改；硬件在提交时判断这次登记是否仍有效。

插入一次异常可能影响这种独占状态。所以框架不能永远把 LDXR 当作普通 LDR，填完寄存器就结束。

uz_llsc_prepare 识别当前独占读取，或向前分析指令以确定独占读取及其地址；uz_llsc_walk 向后解释有限窗口，寻找匹配的条件写入；模型能够完整处理时，uz_llsc_commit 才提交写入和寄存器结果。

这是对受支持序列的有限软件补偿，并没有重新安装原来的硬件独占监视状态，也不能泛化为任意多线程原子程序的完全等价实现。

十一、关键步骤八：撤销覆盖，为什么不能直接释放内存

撤销入口最终进入 release_session。此时可能仍有线程正在异常处理，或者内核代读正在使用会话状态。释放顺序错误，会把这些执行中的路径留在已经不存在的缓冲区上。

图 6：只有硬件不再制造新的受管访问，并且已有读者离开，才能回收影像和描述符。

1. 确认会话可以撤销

后端先检查是否仍有存活的受管子地址空间，以及是否存在不能静止的重放工作。如果还有依赖，返回忙状态，继续保留处理能力。

2. 暂停替代值，排空旧读者

设置 g_suspend 后，仍需处理的受管读取使用原生基准视图。随后切换读者批次，等待已经进入的旧读者完成。

3. 恢复页面权限，清除旧的地址翻译缓存

ap_disarm_pages 恢复符合条件页面的数据访问权限，并进行 TLB 失效。恢复过程中保留过渡状态，以便已经产生、但尚未处理的权限异常仍能找到正确处理入口。

如果权限恢复失败，框架保留会话和缓冲区，而不是冒险释放仍可能被异常访问的存储。

4. 关闭读者入口，等待所有引用归零

此时再关闭新读者入口，并等待两组读者全部退出。等待不能用“过了足够长时间”替代；必须以引用计数确实归零为准。

5. 释放缓冲、索引和地址空间引用

最后，后端把会话置为关闭，释放页影像、描述符、索引、子影像池及持有的 mm 引用。

会话注销与 KPM 模块卸载是不同层次的动作。前者恢复受管页并释放会话对象；后者还涉及宿主挂接代码是否仍在执行。会话读者协议并不能独自证明模块代码可以安全热卸载。
